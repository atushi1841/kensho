## 発見した情報（信頼度付き）

### 1. JA4移行は主要アンチボットベンダーで完了フェーズ（信頼度: 高）
- Cloudflare・DataDome・Akamai・Imperva・F5・AWS WAF(CloudFront)が2026年にJA4/JA4+を本番稼働。CloudflareはJA4をネイティブフィールドとして露出、クライアント側で偽造不可
- JA3はChrome 110のTLS extension permutation（2023年）で死亡。JA4はソート後ハッシュのためシャッフル無効化が効かず、Chrome実環境でも安定ハッシュになる
- JA4+はTLSだけでなく **JA4T（TCPスタック指紋・p0f系）と併合スコア**。TLSが完璧でもTCP層がLinuxスタックなら「iPhone/Windows宣言と矛盾」で弾かれる層がある
- 出典: https://voidmob.com/blog/ja3-vs-ja4-tls-fingerprinting-bot-detection-2026 / https://scrapfly.io/blog/posts/ja3-ja4-tls-fingerprinting-guide-to-detection-and-evasion / https://krowdev.com/article/bot-detection-2026/ （3ソース一致→高）

### 2. Akamai系「2026年クロスバリデーション」の具体像（信頼度: 中〜高、ベンダーブログバイアス考慮）
- User-Agentとプロトコル信号の相互整合チェック: Chrome 131+を名乗るならClientHelloに**ポスト量子鍵共有 X25519MLKEM768**が必須。欠けると即UA矛盾フラグ
- HTTP/2 SETTINGSフレーム指紋（Akamai式fingerprint）と擬似ヘッダー順序も層の1つ。TLSだけ偽装してh2を素の順序で出すと検出
- 「単一信号で弾く」ではなく「層間矛盾1つでセッション失効（<200ms）」＋静かなDegradation（ハニポットデータ返却）が増えた
- 出典: https://proxyhat.com/blog/akamai-bot-manager-v2-deep-dive （一次情報=FoxIO/FingerprintJSへの言及あり、ただしproxy販売ブログ経由なので中）

### 3. 【実測】Kensho現行httpx収集は非ブラウザJA4を露出、curl_cffiで解消可能（信頼度: 高=自前実測）
tls.peet.ws へWSLから直接HTTPSしてJA4を取得:
| クライアント | JA4 | ALPN/h2 |
|---|---|---|
| httpx 0.28（収集common.fetch()） | `t13d1712h1_ab0a1bf427ad_8e6e362c5eac` | HTTP/1.1・h2なし |
| curl_cffi 0.15 impersonate=chrome131 | `t13d1516h2_8daaf6152771_02713d6af862` | h2 |
| curl_cffi 0.15 impersonate=chrome136 | `t13d1516h2_8daaf6152771_d8a2da3f94cd` | h2 |
- httpx版は先頭セグメントから `h1`（HTTP/1.1専用）で素の状態ではブラウザ伪装と即判別される。curl_cffi版は既知Chromeパターンの `t13d1516h2` に一致
- Kenshoは **curl_cffi 0.15.0 + scrapling が既に .venv に入っている** が `config.yaml:184 use_scrapling: false`（無効）。`scraping/sources/scrapling_fetch.py`（TLS指紋偽装フェッチャー）も未使用状態
- 出典: 自前実測 + https://github.com/lexiforest/curl_cffi （信頼度: 高）

### 4. X（旧Twitter）の検出はAPIゲートウェイ4層＋swarm＋時間正規性（信頼度: 中、ベンダー系解析記事の3ソース一致）
- Xは2024年末以降、検出をクライアントJSから**APIゲートウェイへ移動**。全リクエストを (a) Cookieエントロピー (b) デバイス指紋 (c) IP評判（hosting ASNか residentialか）(d) 実タッチ入力の有無 でスコアリング
- 2026年 purge 解析（ピーク分あたり208垢停止・Nikita Bier発言由来）: 停止垢の最大要因は**datacenter/VPS系IP**。同じ行動でも住宅IPはスコアが有意に低い
- **時間パターンは「量」より「規則性」がシグナル**。毎時:00刻みの定時実行はメトロノーム Signature。推奨は ±8〜22分のジッタ＋日次件数 ±2 変動
- swarm検出: リプライ文中のテキスト類似・新規垢クラスタ・複数垢で同一URL共有。**投稿系自動化とエンゲージメント操作を同一セッション内で混ぜるな**（15〜30分の間隔、または手動セッション分離が生存条件）
- プロフィール完全性（2026/2以前の電話確認・アイコン・bio・90日age）はグレーゾーン行為の加重緩和係数として機能。**未整備の新規垢での即自動化は全wave中最高リスク群**
- 出典: https://socialnexis.com/guides/x-june-2026-bot-purge-anatomy / https://notpeople.ai/blog/twitter-x-account-suspended-appeal （2000垢red-team一次実験データ） / https://x.com/proxy_serv/status/2031986060285329581（日本語実況） — 両社とも「垢販売/セchedule SaaS」のマーケティング由来のためバイアス補正で中
- ⚠注意: 「エンゲージメント自動化は絶対禁止」は両社の商品立场を含む。Kenshoの中核（いいね/RT/フォロー）はこのリスク帯の真上にある前提で、**層別対策（IP評判＋指紋＋ジッタ）で相殺する**のが現実解

### 5. 住宅IPプロキシの検出側技術＝Kenshoの分離設計の弱点リスト（信頼度: 高、防御側一次情報的記事）
検出側が積んでいる独立信号（1つでは誤検出、2〜3同時ヒットで弾く）:
1. ASN分類（hosting keyword→即時flag）。KenshoのキャリアAPN（Y!mobile/inobase=au NTTドコモ系モバイルASN）はここを通過しやすい＝現状設計は正しい
2. **TCP/IPスタック指紋（p0f）**: リクエストヘッダがWindowsを名乗り、TCPウィンドウ/MSS/OptionsがLinuxカーネルならトンネル即疑い→ **WSL内Pythonから応募したら出口がWindows Chromeでもヘッダ/スタックが割れる恐れ**。現行はWindows Chrome CDP応募でOK
3. **レイテンシ三角測量**: IP geolocation と RTT の物理的矛盾（東京IPなのにRTT 300ms）→ Kenshoは出口IP=実機接続なので無関係。Apify等バックコントラクト経由に転用時は注意
4. **指紋fanout**: 多数の別々住宅IPが1個の稀なTLS指紋を共有＝同じボットツール。Kenshoは各垢実Chromeだが、同一WindowsマシンのChromeバージョンが揃うため「数垢同一JA4」は当然発生。XがJA4+swarm結合で見る可能性は残る
5. Device→IP逆回転（1端末が多数IPを行き来）: Kenshoは垢ごと固定出口=回避済み（9/8の切り替え事故は逆方向）
- 出典: https://ipasis.com/blog/detecting-residential-proxies-techniques / https://blog.crawlex.net/blog/residential-proxy-asn-detection/ （2ソース一致→高）
- X検索での日本語一次報告: 2026/3/12スパム検知強化でアンケート連発・大量フォローがAI検知強化（https://x.com/proxy_serv/status/2031986060285329581 / 低〜中、単発）
