# X API変更・レート制限・TOS変更 調査レポート（2026-09-27）

## 1. 発見した情報（信頼度付き）

### 1.1 X API 料金体系の根本的変更（2026年2月〜）
- **無料枠の完全廃止**（新規開発者向け） [Sorsa 2026/07/31 / 信頼度: 高]
  - 旧Free/Essential/Elevatedティアは2023年2月に終了
  - 2026年2月6日以降、新規開発者は「従量課金（pay-per-use）」のみ利用可能
  - Legacy Basic ($200/月) と Pro ($5,000/月) は既存加入者のみ継続可能、新規受付停止
- **従量課金の実態** [SocialCrawl 2026/06/26 / 信頼度: 高]
  - 読み取り: $0.001〜0.01/リクエスト、書き込み: $0.015〜0.20/リクエスト（URL含むと$0.20）
  - 月間200万投稿読み取りのハードキャップあり
  - 開発者コンソールでクレジット管理、事前入金なしではAPI通信が弾かれる
- **自社確認**: KenshoはPlaywright/CDPによるブラウザ自動化で運用中、公式API未使用のため**課金影響は直接なし**だが、仕様変更の波及リスク大

### 1.2 2026年4月20日：エンゲージメント系APIのEnterprise専用化（重要）
- **以下の書き込みエンドポイントが全セルフサーブティアから削除** [Sorsa / TwitterAPIs / API.sorsa.io 2026/03/24, 07/31 / 信頼度: 高]
  - POST /2/users/:id/likes（いいね）
  - POST /2/users/:id/retweets（リポスト）
  - POST /2/tweets（引用ポスト含む）
  - POST /2/users/:id/following（フォロー）
- **影響**: Kenshoの懸賞応募（いいね＋RT＋フォロー）が公式API経由では**完全に不可能**に
  - 代替: ブラウザ自動化（現行方式）のみが残る手段
  - ただし公式TOSではブラウザ自動化・スクレイピングは明確に禁止

### 1.3 レート制限の三層構造（2026年7月時点最新） [Sorsa 2026/07/31 / 信頼度: 高]
| 層 | 制御対象 | 例 | Kenshoへの影響 |
|---|---|---|---|
| APIレート制限 | エンドポイントごとの呼出速度 | 最近検索 300/15分/ユーザー | 収集フェーズで直撃 |
| 使用量キャップ（課金） | 月間データ消費量 | 従量課金で200万投稿読み取り/月 | 公式API不使用なら無関係 |
| アカウント制限 | Xアカウント自体のプラットフォーム制限 | 未認証: 50投稿/日、200リプライ/日 | **応募ボリュームの実質上限** |

- 未認証アカウントの投稿上限が2026年5月に**2,400→50/日へ大幅削減**
- Kenshoは1アカウント50〜75件/日運用のため、**アカウント制限ギリギリ**で運用中

### 1.4 自動化ルール・BOT検出の大幅強化（2026年3月〜） [Unfollr 2026/04/08 / OpenTweet 2026/02/19 / 信頼度: 高]
- **2026年3月「不正行為（inauthentic behavior）」バン波**発生
- **即座BANトリガー**: 大量フォロー/アンフォロー、自動いいね、エンゲージメントポッド、リプライスパム、自動DM、フォローチャーン
- **検出ロジック**: タイミング規則性、アクション速度、セッションパターン、コンテンツパターン、API指紋、ネットワーク分析（複数垢の相関）
- **公式ガイドラインの核心**: 「公式APIのみ使用可」「自動化アカウントはボットラベル必須」「ユーザー主導でない相互作用禁止」「レート制限遵守」[X公式 Developer Guidelines / 信頼度: 高]

### 1.5 Kensho現状のリスク評価
- **応募実績**: 2026W38で2,020件応募、当選15件（当選率0.4〜0.7%）[weekly_win_analysis_2026W38.md / 信頼度: 高]
- **運用方式**: Playwright + Chrome CDP（ポート9222）によるブラウザ自動化
  - 公式API不使用＝課金回避だが、TOS上は「スクレイピング/ブラウザ自動化禁止」に該当
  - IP分離（USBハブ経由SOCKS5プロキシ、垢×WiFiマッピング管理済み）で対策中
- **直近インシデント**: 2026/09/24に2垢凍結（inobase128508, chugakujuken）→ configのbatchesコメントアウトで応募停止、accountsからは外さずproxy_watchdog復旧維持

### 1.6 スクレイピング・非公式アクセスの法的リスク
- XはスクレイピングをTOSで明確禁止、Nitter等フロントエンドは2024年初期に機能停止 [SocialCrawl / Scrapfly 2026/08/27 / 信頼度: 中]
- 訴訟事例あり（Xがスクレイパー提訴）、ただし個人利用レベルでの訴訟実例は限定的
- 日本国内では「懸賞応募自動化」の法的グレーゾーン（景品表示法・不正競争防止法の適用範囲が曖昧）

## 2. Kenshoへの適用提案

### 提案A：アカウント制限（50件/日）を厳守し、ブラウザ自動化を継続・最適化
- **期待効果**: 現行運用の継続、追加コストなし、当選実績の積み上げ
- **実装コスト**: 低（設定値調整のみ。1アカウント50件/日、1セッション15〜20件、1時間20件上限の現行ルールを厳守）
- **リスク**: **高** — TOS違反（ブラウザ自動化）、アカウント凍結リスク恒常化、X側検出強化で突然全垢BANの可能性
- **優先度**: 高（現実的な継続手段として当面必須）

### 提案B：公式API移行の検討（Enterprise契約または代替API活用）
- **期待効果**: TOS準拠、安定稼働、スケール可能
- **実装コスト**: **極大** — Enterpriseは月$42,000〜、代替API（Sorsa/SocialCrawl等）も月$49〜且つ「いいね/RT/フォロー書き込み」は提供されない可能性大
- **リスク**: 費用対効果が合わない（月1〜3万円収益目標に対しコスト過大）、エンゲージ書き込み不可なら懸賞応募要件を満たせない
- **優先度**: 低（現収益規模では非現実的）

### 提案C：「人間らしさ」シミュレーションの強化（BOT検出回避）
- **期待効果**: 凍結リスク低減、アカウント寿命延長
- **実装コスト**: 中（ランダム遅延の分散拡大、マウス移動/スクロール模倣、セッション間隔の曜日ローテーション、リプライ文言の多様化、アカウントごとの行動パターン差別化）
- **リスク**: 中（完全回避は不可、検出アルゴリズム更新で無効化される可能性）
- **優先度**: 高（提案Aとセットで実施必須）

### 提案D：データ収集のみ公式API（読み取り専用）へ移行、応募はブラウザ自動化維持
- **期待効果**: 収集フェーズの安定化・高速化、レート制限ヘッダー活用で効率化
- **実装コスト**: 中（従量課金で読み取りのみなら月数ドル〜数十ドル、kensho_collect.py書き換え必要）
- **リスク**: 低（読み取りのみならTOS準拠しやすい）
- **優先度**: 中（収集安定化の切り札、応募フェーズはブラウザ継続）

### 提案E：垂直ニッチ特化のデータ販売（Apify/MCP化）で収益多角化
- **期待効果**: 懸賞データという独自資産のマネタイズ、API販売で「売る労力」最小化
- **実装コスト**: 中（MCPサーバ化、Apify Actor出品、スキーマ整備）
- **リスク**: 低（データ販売はTOSグレーゾーンだが「売る」側なので凍結リスクと非対称）
- **優先度**: 高（notepad lessonsの次アクションと整合）
