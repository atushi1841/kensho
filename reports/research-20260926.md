### 1. Kenshoの静的HTTP経路はTLS層で本物Chromeと同一 JA4（実測・信頼度: 高）
- Kensho venv の curl_cffi 0.15.0 で tlsinfo.me/json に到達し JA4 を実測:
  - `chrome136` / `chrome142` → `t13d1516h2_8daaf6152771_d8a2da3f94cd`
  - `chrome124` / `chrome131` → `t13d1516h2_8daaf6152771_02713d6af862`
  - `safari17_0` → `t13d2014h2_a09f3c656075_14788d8d241b`
  - `chrome137` → ImpersonateError（未対応）
- 外部記事の既知JA4と照合: `..._02713d6af862` = Chrome 120–131、`..._d8a2da3f94cd` = Chrome 133–136+（krowdev.com/article/bot-detection-2026/ 信頼度: 中〜高、FoxIO JA4・Cloudflare blog を一次引用）
- → collect系の静的リクエストは TLS+HTTP/2 レイヤーで「本物のChrome」と矛盾しない。JA3 は Chrome 110 以降毎回ランダム化され实用価値を失ったが JA4 は安定ハッシュなので現行標準（信頼度: 高、FoxIO仕様+Cloudflare 15M JA4統計）。
- 注意点: **impersonate に存在しない名前（chrome137）を刻むと例外で落ちる**。「最新名をコードで刻む」運用は脆弱。

### 2. 検出は7層構造・「クロスレイヤー整合性（stack drift）」が真 Gate（信頼度: 高）
- TCP/IP(JA4T) → TLS(JA4) → HTTP/2 SETTINGS・疑似ヘッダ順序 → HTTPヘッダ順序 → Client Hints整合 → IP/ASN → 行動、の順にJS実行前に判定（krowdev 2026、FP-Inconsistent IMC2025・Cloudflare blog を一次引用）
- 「完璧なTLS＋間違ったHTTP/2設定」は「両方ふむり」より**より怪しい**。
- 非JSリクエストでは canvas/WebGL/行動分析は「theater（効かない）」→ TLS+H2+ヘッダの3層が全て。JP語ソース（Qiita等）はアフィリエイト系が多く一次性低、除外。

### 3. Layer 0: プロキシとUAのOS不一致（TTL）（信頼度: 中）
- SOCS5/CONNECT経由ではターゲットは**プロキシ側TCPスタック**（多くはLinux TTL=64）を見る。Windows UA と TTL=64 の不一致は検出材料（krowdev / Zardaxt・p0f 一次）。
- Kenshoへの含意: **データセンター系Linux SOCKS5 + Windows Chrome の組合せに理論上該当**。RM10JE_S等の住宅回線系はルータ透過で見た目がユーザー側挙動になり影響小。
- X/Twitter が実際に JA4T を使っているかは未証明 → 要検証。
