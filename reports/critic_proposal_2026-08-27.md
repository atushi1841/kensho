### 提案38【中・実装推奨】applier keyword_flag再判定のtweet_text優先化（即効）

**問題:** applierのCDN再判定（f4c2ce1, line 636-642）は `api_get_tweet_text(page, tweet_id)` でREST（死）→CDN再フェッチ（ネットワーク依存）を毎回行う。CDNがレート制限・タイムアウトで失敗すると `_flag_recheck_text=""` となり、過検出項目も誤ってスキップされる。

**証拠（実測）:**
- keyword_flag 327件中281件（85.9%）が収集時tweet_text上では過検出
- 収集時tweet_textは**全327件に存在**（0件欠落なし）
- 収集時tweet_textで判定すれば281件が確実に解除（CDN依存なし）

**修正内容（applier.py line 639-642）:**
```python
# 旧: CDN再フェッチのみ
_flag_recheck_text = ""
if _flag_tweet_id:
    try:
        _flag_recheck_text = api_get_tweet_text(page, _flag_tweet_id, log_fn=out)
    except Exception:
        _flag_recheck_text = ""
# ↓ 新: 収集時tweet_textを優先、未取得時のみCDN再フェッチ
_flag_recheck_text = item.get("tweet_text", "") or ""
if not _flag_recheck_text and _flag_tweet_id:
    try:
        _flag_recheck_text = api_get_tweet_text(page, _flag_tweet_id, log_fn=out)
    except Exception:
        _flag_recheck_text = ""
```

**変更量:** 2行修正（1行追加 + 1行変更）

**副作用:**
- 収集時tweet_textが古い場合でも、has_skip_keywordはキーワード有無のみ判定（キーワードはツイート上で変化しない）→ 問題なし
- 削除済みツイートでも収集時tweet_textは有効 → 問題なし
- 締切切れ判定（line 621-628）は別処理で正常動作 → 問題なし

**リスク: 低**（has_skip_keywordは既存関数。tweet_textがある場合のフォールバック順序変更のみ）

**期待効果:**
- 281件の過検出が確実に解除 → 応募プールが回復（変換率 23.4% → 40%超）
- 収集時tweet_textがない場合のみCDN再フェッチ（ネットワーク呼び出し削減）
- セッション時間節約（281件 × 3-10秒 = 14-47分/全バッチ）
