## 提案24【高】keyword_flag過検出是正 — applierでCDN tweet-text再判定

### 状況
- b70b5d4（23:30）でkeyword_flag実装完了。ただしcpmeikan/kenkakuのHTMLコンテキスト判定は過検出（288件中半数以上が誤判定）。
- サンプル検証で通常のフォロー+リポスト応募が誤判定されていることを確認。
- 収集時にtweet_textが取得できないソース（cpmeikan/kenkaku）は、収集時にCDN tweet-textを取得していない。

### 提案内容

applierのkeyword_flagスキップ（line 632-634）を、以下の二重チェックに変更する:

```python
# 現状（line 632-634）:
if item.get("keyword_flag", False):
    out(f"  [{global_idx}/{max_n}] [SKIP] 引用/コメント応募 → AI対応不可のためスキップ")
    continue

# 修正案:
if item.get("keyword_flag", False):
    # CDN tweet-textで再判定（収集時のHTMLコンテキストは不正確な場合がある）
    tweet_text = item.get("tweet_text", "") or ""
    if not tweet_text:
        # tweet_textがない場合はCDNから取得
        tweet_id, _ = extract_tweet_id_and_screen_name(clean_url)
        if tweet_id:
            try:
                tweet_text = _cdn_get_tweet_text(tweet_id, log_fn)
            except Exception:
                pass
    if tweet_text and not has_skip_keyword(tweet_text):
        # CDN本文ではキーワードが検出されない → 収集時の誤判定
        out(f"  [{global_idx}/{max_n}] [SKIP] 引用/コメント応募（CDN再判定: 収集時誤判定の可能性）→ スキップ")
        # 応募機会を逃さないため、keyword_flagを無視して処理継続
        # またはログだけ残してcontinue
```

**重要な判断:** 過検出を許容して応募機会を損失するリスク vs 誤検出を見逃してBOTシグナルを発生するリスク。前者（応募機会損失）の方が現実的に大きいため、**CDN再判定でtweet-textにキーワードがなければ処理継続**が安全。

**代替案（より安全）:** 収集時のcpmeikan/kenkakuのhas_skip_keyword判定を、HTMLコンテキストからCDN tweet-text取得に変更する（収集時にCDNを呼ぶため遅くなるが、判定精度が向上）。

**危険度: 中**（過検出により応募機会を損失。ただし現在の応募プールは942件未応募+651件keyword_flag=Falseが存在するため、直ちに応募枯渇にはならない）

**期待効果:** 288件の誤判定を是正し、実質的な応募機会を回復。応募数が5-10件/日増加する可能性。

**検証方法:** 修正後、collected.jsonのkeyword_flag=Trueアイテムのapplied率を確認。8/26のapplied済みkeyword_flag 80件（修正前）と比較して、適正な割合で応募されているか確認。
