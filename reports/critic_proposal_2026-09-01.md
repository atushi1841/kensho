## 🔴 重大発見: inobase1-4 フォローAPI code 64（アカウント停止）

### 事実（実ログ・audit実測）
- 11:06/11:13/11:17/11:32/11:35/11:38 JSTにフォローAPIが **HTTP 403 code 64 "Your account is suspended"** を6回返却
- **フォロー403×3でFROZEN_ABORT発動（11:38）→ バッチ即時中断**（提案90/91が正常動作）
- **ただし like/rtは11時台以降も14件成功継続**（11:04〜11:37 rt/like OK）→ **完全凍結ではなく「フォロー専用制限」パターン**
- 12:00/12:15/12:30バッチはセッション確認のみで「垢別起動」なし → FROZEN_ABORT後の停止が機能
- 8/31は87件成功（CAPTCHA解除で復帰済み）→ **9/1 11時台から突然フォロー制限**

### 解釈
- code 64メッセージは「アカウント停止」だが、like/rt（GraphQL）は成功 → X側の**フォロー機能限定の制限**（follow limit / follow restriction）と推定。完全凍結（読み取り専用）ならlike/rtも失敗するはず
- **当選条件（フォロー＆RT＆いいね）のフォローが不能** → 実質応募不能状態。like/rt成功は「応募成立」にならない

### 対応
1. **【要ユーザー対応】**: ブラウザで @inobase128508 にログインし、フォロー制限/停止バナーの有無・CAPTCHA再要求を確認（ACCOUNT_SAFETY_RULES手順3: fxtwitter確認済み=404 → suspended示唆）
2. **自動側**: prop102で「code 64検出時の自動フォロー停止」を実装（下記）

## 新規提案（1件）

### prop102【高】: code 64（アカウント停止/フォロー制限）検出時の自動フォロー停止
- **根拠（実測）**: inobase1-4でフォローAPI code 64×6（11:06-11:38）。提案93はcode 326（一時ロック）のみ対象で、code 64（停止）は未対応。FROZEN_ABORTはバッチ中断するが「次のバッチで再起動→再失敗」の繰り返しリスク（toushiwatchの轍）
- **提案**: `_is_temp_lock_326` と同様に `_is_follow_suspended_64` を追加。code 64検出時はその垢の**フォローを当日停止**（like/rtも当選条件を満たせないため実質停止推奨）。config除外と同等の効果を自動で実現
- **期待効果**: 停止垢の無駄なバッチ起動・失敗アクション繰り返しを防止。toushiwatch（0成功31失敗）と同じ無駄ループを回避
- **実装コスト**: 低（api_actions.py/applier.pyに既存326ロックと同構造を追加）
- **リスク**: 低（安全機構の拡張。既存FROZEN_ABORTと補完関係）
- **優先度**: 高（当選不能垢の無駄動作を即防止）
