## 提案6【新規・中】proxy_watchdog.py の powershell.exe フルパス化 — 自動復旧が機能していない

**状況（02:15ログ実測・決定的証拠）:**


**根因:** `kensho/utils/proxy_watchdog.py` の `powershell.exe` 呼び出し**6箇所すべて**（89, 183, 211, 228, 236, 286行）がフルパス未指定。cron環境（`PATH=/usr/bin:/bin`）では解決不能 → exit 127。**2026-08-20にwifi_watchdogで修正済みの既知パターン**（`PS=/mnt/c/WINDOWS/System32/WindowsPowerShell/v1.0/powershell.exe`）がproxy_watchdogに未適用。

**影響:** 「アダプタが生きていれば自動復旧する」設計（9933645のorchestrator組込）が**常に失敗**。今回の1085/1089は物理原因（スマホ側）で復旧不能だが、**将来アダプタが復旧したシナリオでもプロキシ自動再起動が効かない**。zin(1084)が復旧できたのはDispatcher/wifi_watchdog経由のため。

**アクション:**
1. proxy_watchdog.py 冒頭で `PS = "/mnt/c/WINDOWS/System32/WindowsPowerShell/v1.0/powershell.exe"` を定義し、6箇所を置換（wifi_watchdogと同じパターン）
2. 再起動コマンドの `subprocess.run(restart_cmd, ...)` も同様
3. 検証: `env -i PATH=/usr/bin:/bin bash -c 'python -c "..."'` でcron環境を再現してテスト

**危険度: 中**（コード修正だが既存の実績あるパターンの適用のみ。実行ロジック変更なし）/ **期待効果: プロキシ自動復旧の信頼性回復。アダプタ復旧→自動復旧の循環が機能し、手動介入の頻度が減る**

**✅ 実装済み（2026-08-26 02:47 Worker）:** `kensho/utils/proxy_watchdog.py` 冒頭に `PS = r"/mnt/c/WINDOWS/System32/WindowsPowerShell/v1.0/powershell.exe"` を定義し、6箇所（`_adapter_ipv4` / `Get-NetAdapter`×2 / `netsh wlan disconnect` / `netsh wlan connect` / restart_cmd）を `powershell.exe` → `PS` に置換。cron環境（PATH=/usr/bin:/bin）で `_adapter_ipv4("kudou_RM10JE_B")` → `10.32.223.239` を実測（フルパスでPowerShell実行成功）。pytest 148 passed / mypy 新規エラーなし（既存2件のみ）。コミット: 下記Worker報告のハッシュ参照。

## 根因分析

**12bd9faの2つの変更が複合して回帰:**

| 変更 | 行 | 問題 |
|------|-----|------|
| `verify_unresolved→失敗化`（verifier.py 198-205行） | 1168/1177/1186行 `_per_item_ok[...] = False` | **APIで成功したアクションがVERIFYで覆される** |
| VERIFY失敗時failure_tracker記録 | 1197-1204行 | 連続3回でCEILING→残りスキップ |
| VERIFY例外時record_failure | 1193行 | **Page.gotoタイムアウト（Xが遅い/プロキシ不安定）も「アクション失敗」としてカウント** |

**本質:** VERIFY（ページ再読込でボタン状態確認）は「APIの偽装成功を検出する」目的で導入されたが、12bd9faで「VERIFYが失敗＝アクション失敗」と単純化された。VERIFYの失敗原因の大半は「ページロードタイムアウト（Xの応答遅延・プロキシ不安定）」「button_unresolved（UI判定不能）」であり、**アクション自体の失敗ではない**。今日のVERIFYタイムアウトは200件（全バッチに分散）。

**実害:** `[OK] RT（API）`が成功してもVERIFY失敗で `_per_item_ok["rt"]=False` → applied付与なし → 次サイクルで再処理。さらに連続3回でCEILING発動 → そのバッチの残りアイテム全部スキップ。今日のCEILING 26件のうち少なくとも1件（14:18）はこの連鎖。

## 提案8【高・新規・回帰修正】VERIFY失敗をfailure_tracker/CEILINGから分離する

**アクション:**

1. **API成功時はVERIFY失敗で `_per_item_ok` を覆さない**（1168/1177/1186行）:
   ```python
   # 旧: _per_item_ok["rt"] = False
   # 新: API成功(_rv)していない場合のみVERIFY失敗で覆す
   if not _per_item_ok.get("rt"):
       _per_item_ok["rt"] = False
   ```
   → API成功（`[OK] RT（API）`）があれば、VERIFY失敗でも応募成立を維持。VERIFYは「偽装成功の検出」であり「成功の取り消し」ではない。

2. **VERIFYのPage.gotoタイムアウト（1193行 except）をfailure_trackerから除外**:
   - Page.gotoタイムアウトはネットワーク/X側の問題。アクション失敗と同列にしない。
   - 代わりに「リトライ1回 or DEFER相当の扱い」にする。

3. **CEILINGカウントは「アクション実行自体の失敗」（API失敗・UIフォールバック失敗）に限定**:
   - VERIFY失敗はカウントしない（または別カウンタで監視のみ）。

**危険度: 中**（12bd9faの意図「偽装成功の水増し防止」を維持しつつ、API成功アクションを守る。ただし偽装成功（API 200だが実際未反映）の検出感度は下がる可能性 → フォロワー実測での乖離監視を併用）

**期待効果:**
- CEILING誤発動によるバッチ打ち切りを防止（応募機会の損失を解消）
- API成功アクションが再処理されず無駄な二重アクション（BOT信号）を防止
- VERIFYタイムアウト200件/日の影響をゼロ化
