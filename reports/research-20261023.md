# 調査レポート（2026-10-23 / プロキシ・TLS・ブラウザフィンガープリント）

## 発見した情報

### 1. Canvas/Fingerprinting検知の進化（信頼度: 高）
- **出典**: 
  - Castle.io: "Detecting noise in canvas fingerprinting" (2026-03)
  - UC San Diego: "Characterizing Canvas Fingerprinting Use Across the Web" (IMC25)
  - BrowserInsight: "How Sites Detect Anti-Detect Browsers" (2026-10)
- **内容**: 
  - Canvas指紋は依然として主要なBot検知手法。WebAssemblyで隠蔽・難読化が進化中
  - フィンガープリンティングスクリプトは"canvas inconsistency check"（同一キャンバス複数描画で差異を検出）を45%実施。これによりノイズ注入対策は検知可能
  - 高度なspoofingは「セッション毎のノイズ注入」+「GPU文字列偽造」を実装、ただしGPU能力値との整合性チェック（MAX_TEXTURE_SIZE, extensionリスト等）が新たな検知ポイントに
  - CreepJS等の「整合性スコアリング」手法により、単体spoofingではなく「複数シグナルの一貫性」が検知対象に

### 2. TLS/HTTP2フィンガープリント自動化（信頼度: 高）
- **出典**: GitHub scrape-hub/koon (2026, Rust+Python/Node/R)
- **内容**:
  - koon: TLS (JA3/JA4), HTTP/2 (Akamaiハッシュ), HTTP/3 (QUIC JA4) をブラウザごとに完全再現
  - 357プロファイル対応: Chrome 131-155, Firefox 135-157, Safari 15.6-27.0, Edge, Opera, Brave等
  - Akamai, Cloudflare等のBot検知は接続ファースト評価（TLS→HTTP→JS）。koonはTLS/HTTP2レベルで通過し、その後必要ならブラウザ誘導
  - 注意点: OS-TCPフィンガープリント（TTL, TCP window size）はカーネル層のためプロキシOSと一致させる必要あり

### 3. ブルーチーム視点: GPU整合性チェック（信頼度: 高）
- **出典**: The Audit Veteran (2026-03), ignifexlabs.com
- **内容**:
  - WebGL拡張・canvas noise注入は「GPU能力値パラメータ」との不一致で検知可能
  - 例: "NVIDIA GeForce GTX 1650" を詐称しても MAX_TEXTURE_SIZE=32768, extensionリスト, GLSL precision値がSwiftShader（ソフトウェアレンダラ）基準なら即検出
  - 完全なspoofingにはopen-sourceライブラリ（GitHub複数存在）で full-surface WebGLパラメータセットを上書き必要

### 4. proxy種類と検知リスク比較（信頼度: 中）
- **出典**: niespodd/browser-fingerprinting GitHub, 業界報告
- **内容**:
  - Datacenter proxy: 安価だがIPプールが限定的、BrightData/Oxylabsは主要プロバイダ
  - Residential proxy: 高コストだが検知リスク低、 geo-restriction回避に有効
  - X（Twitter）懸賞応募: 1アカウント1IP分離が必須（atushi16のみ自宅IP、他はproxy）は継続必須
  - Mobile proxyは未調査（X scrapingにおいて特に有効か要検証）

### 5. 実装戦略パターン（信頼度: 中）
- **出典**: niespodd/browser-fingerprinting GitHub
- **シナリオ別アプローチ**:
  - short-lived sessions（Auth不要）: rotating IP + 軽量fingerprints → X懸賞「応募」シナリオ与此類
  - long-lived sessions（Auth要）: stable IP + consistent fingerprints → ソーシャル管理用途
  - JS-based detection: puppeteer-extra-plugin-stealth 等
  - full fingerprint: 完全一致レプリケーション（Stripe/Adyen級）→ Kenshoは現状不要レベル

## Kenshoへの適用提案

### 提案1: koonによるTLS/HTTP2フィンガープリント改善（優先度: 中）
- **内容**: 収集パイプライン（kensho_collect.py）でkoon(Python)を利用し、TLS JA4/JA3をChrome/Firefoxプロファイルに統一
- **期待効果**: Cloudflare/Akamai等のTLS層Bot検知を回避、収集成功率向上
- **実装コスト**: 中（koon pip install + 既存requests/httpx置換 + プロファイル設定）
- **リスク**: 低（オープンソース、MITライセンス）
- **検討事項**: 現時点でX収集はブラウザ経由なので低優先度。knshow.com/ken-kaku.com等では有効可能性あり

### 提案2: Canvas/Fingerprint整合性テストの実装（優先度: 低）
- **内容**: Kensho運用環境でbrowserleaks.com/pixelscan.net等でフィンガープリント評価を実測
- **期待効果**: 現在のプロキシ/IP分離が十分か検証、改善ポイント特定
- **実装コスト**: 低（手動テスト or 定期スクリプト）
- **リスク**: 極めて低
- **検討事項**: XはブラウザJS実行ベースなのでCanvas spoofingは既存auto-detectブラウザで対応済み。新規リスクは低い

### 提案3: GPU整合性チェック回避（優先度: 低）
- **内容**: headless browser使用時にWebGLパラメータの一貫性検証
- **期待効果**: WebGL基盤の高度Bot検知を回避
- **実装コスト**: 高（full-surface WebGL spoofing実装が必要）
- **リスク**: 中（保守コスト、ブラウザアップデート追従）
- **検討事項**: Kensho现状では不要。X応募は通常のブラウザインスタンス使用

### 提案4: proxy OS整合性確認（優先度: 高·即時検証）
- **内容**: 現在使用中の各SOCKS5 proxyホストのOS（Linux/Windows）を確認し、TLS TCPフィンガープリントと一致させる
- **期待効果**: OS-TCP不一致による検知リスク低減
- **実装コスト**: 低（os_checkスクリプト + 必要に応じproxy変更）
- **リスク**: 低
- **重要**: 現在atushi16は自宅IP（Windows）、他垢はUSB HUB経由でIP分離。各proxyホストのOS確認が急務

### 提案5: 定期的フィンガープリントモニタリング（優先度: 中）
- **内容**: 週次でbrowserleaks.com/fVision等にて各アカウントのフィンガープリントを自動計測・記録
- **期待効果**: 異常値早期発見、検知リスク定量化
- **実装コスト**: 中（スクリプト実装 + ストレージ）
- **リスク**: 低
- **検討事項**: kensho/utils/ にフィンガープリントヘルスチェック追加
