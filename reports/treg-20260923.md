## 0. 結論（先に3行）

1. **tregはテキストLLMのルーターではない**（README: "OpenRouter, but for agent tools **instead of models**"）。よって **KenshoのLLMコスト最適化には構造的に使えない**。LLMは現行方針（nous無料枠 > fireworks > OpenRouter無料枠）を維持する。
2. **転換率は「公開・実測値」が存在する**（成功率 ok_rate と有効結果率 hit_rate、サンプル数付き）。ただし意味は「呼び出し→有効結果」の歩留まりであり、**登録→課金の転換率は非公開（実測不能）**。
3. **Kenshoの収益チャネルにはならない**（公開カタログは運営curated、自前登録ツールはチーム内私有）。→ **見送り**。唯一の吸収価値は「同一capabilityを価格×成功率×歩留まり×レイテンシの4軸で並べる」計測思想（Apifyアクター選定・価格設定の参照）。

## 4. Kenshoへの適用判定

| 用途 | 判定 | 根拠（実測） |
|---|---|---|
| **LLMコスト最適化** | **不可** | tregはtools専用（"instead of models"）。テキストLLMルーティング機能なし → 現行 nous>fireworks>OR無料 を維持 |
| X読み取り（プロフィール/投稿） | **見送り** | `x_link_reader.py` の fxtwitter無料経路が既にある。第三者X APIは垢特定・TOS・IP分離原則と衝突（Xquik判定と同一） |
| 収益チャネル（自ツール販売） | **不可** | 公開カタログは運営curated。チーム登録ツールは私有（販売マーケットではない） |
| BYOK（Apify鍵をtreg経由で共有） | **不要** | Kenshoは既にApifyを直叩き。中間層は遅延・障害点を増やすだけ |
| データ調達の価格ベンチマーク | **採用（思想のみ）** | 同一capabilityの 価格×ok×hit×p50 を公開する計測方式は、Apifyアクター選定・値付けの参照になる |

### 提案（Verifiability Constraint準拠・優先度: 低）
- 提案: **tregへの登録・課金・追跡は行わない**（追加タスクを作らない）。元提案の問題設定「KenshoLLMコスト最適化での活用」はtregの仕様上成立しないため、**クローズ**。
- 成功指標: 本レポートの数値で判定済み（追加支出 **0円**、追加登録 **0件**）
- 検証コマンド: `grep -c '転換率\|価格\|登録' /mnt/d/Project2/kensho/reports/treg-20260923.md`
- 失敗時代替: 数値裏取りが取れない場合は既存READMEのみで結論（今回は実HTTPで取得済みのため不要）
