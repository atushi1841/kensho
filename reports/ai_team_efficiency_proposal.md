# Kensho AIチーム（Critic/Worker/QA）自己改善ループの運用効率化提案
本提案は、2025年〜2026年の最新AIエージェント研究およびプロダクション導入のベストプラクティス（Reflexion, ACE/MCE, Progress Delta, Debounce Hooks等）を調査し、Kenshoの自律運用チームに適用するための具体的な施策をまとめたものです。

---

## 1. 最新ベストプラクティス調査成果（2025〜2026年）

自律型マルチエージェントや自己改善ループ（Self-Improving Loop, Ralph Loop等）を商用/本番環境で安定稼働させるための最新の設計パターンは、以下の4つに集約されます。

### ① エージェント間の連携とコンテキスト圧縮 (ACE / MCE / TOON)
*   **ACE (Agentic Context Engineering) [Lil'Log 2026]**:
    *   コンテキストを単なる静的なプロンプトや単に肥大化する対話履歴として扱わず、**「進化するプレイブック（Evolving Playbook / Structured Logbook）」**として定義。
    *   教訓やルールをフラットなテキストではなく、**`(ID, 説明)`という「構造化された箇条書き（Itemized Bullets）」**としてカプセル化。Curator（エージェント）が追加・修正し、決定論的なロジック（Deduplication）でマージする。
*   **MCE (Meta Context Engineering) [Lil'Log 2026]**:
    *   「どうコンテキストを管理するか（メタレベル）」と「何がコンテキストにあるか（ベースレベル）」を分離。コンテキスト生成ロジック自体を最適化ターゲットにする。
*   **TOON (Token-Optimized Object Notation) & Model Tiering [MindStudio 2026]**:
    *   JSONよりもトークン消費が極めて少ないコンパクトな表現記法（TOON）を採用し、不要なメタデータをそぎ落とす。また、タスクの難易度に応じて適切なLLMにルーティングする（Model Tiering）ことで、全体のトークンコストを **65%〜85% 削減**。

### ② 停滞・無限ループ・偽Doneの防止 (Progress Delta / Debounce / Clear States)
*   **Progress Detection (進捗差分検出) [Meritshot 2026]**:
    *   従来の「最大ステップ制限（ステップカウンター）」は回路遮断器（サーキットブレーカー）に過ぎず、根本解決にならない。
    *   状態オブジェクト（State）に、**「完了したサブゴール一覧」**と**「未完了のサブゴール一覧」**を明示的に持たせる。
    *   直近のステップで未完了サブゴールが減少したかを示す **`Progress Delta（進捗差分）`** を算出し、これが**2ステップ連続で 0（進捗なし）** の場合に、無限ループや停滞と判定して即座にエスカレーション（手動切り替え・プロセス停止）を行う。
*   **Debounce Hook [AWS 2026]**:
    *   LLMは「あともう1回で成功するはず」と誤認して同じAPI/ツールを空回りさせやすい。
    *   ライフサイクルフックに「Debounce Hook」を導入し、スライディングウィンドウ（直近3アクションなど）で**「同一のツール名＋同一の入力引数（パラメータ指紋）」**が2回以上出現した際、3回目の実行を自動遮断し、LLMにエラーとして返す（`BLOCKED: Duplicate call detected`）。
*   **明確な終端状態 (Clear SUCCESS/FAILED States) [AWS 2026]**:
    *   ツールの返却値を曖昧にしない（例: 「さらに結果が得られる可能性があります」などの表記はループを誘発する）。
    *   APIやツールは、LLMに対して `SUCCESS: <ID>` または `FAILED: <理由>` という極めて明確な終端状態を返すように設計することで、ツールの空回りを **7分の1（14回→2回）に削減**。

### ③ 継続的学習と永続化 (Trajectory & Meta-Methodology)
*   **メタ・メソドロジー (Harness as Optimization Target)**:
    *   一時的なインコンテキストの「自己批判（Self-Refine）」は、その場限りの最適化に留まり、長期的な学習にならない。
    *   実行プロセス（Trajectory）から成功・失敗のエッセンスを抽出し、ファイルシステムや永続メモリに格納、これを次のイテレーションで読み込むことで、**「解き方そのものを進化させるハーネス」**を構築する。

## 2. Kenshoにおける現状の強みと課題

Kenshoには、すでに世界最先端の「自律運用ハーネス」が組み込まれています。

### Kenshoの強み（すでに実装済みの優れた仕組み）
1.  **3エージェント自己改善ループ（Critic/Worker/QA）**:
    *   `nightly-critic` / `nightly-worker` / `nightly-qa` による自律ループ。
2.  **Notepad（永続教訓ストア）**:
    *   `hermes cron notepad` を用いて、最大5件、日付付き、長文禁止の箇条書きに制限した鮮度高き教訓永続化。
3.  **Kanbanボード同期と健康度スコアリング**:
    *   `kensho-ai-team` ボードでタスクライフサイクルを管理し、`loop_health.sh` で0-100点評価、停滞 streak 監視（≥3で要ユーザー対応エスカレーション）。
4.  **Done Guard (kanban_done_guard.py)**:
    *   証跡レポート作成、未コミットコード・未pushのチェック、タスク所有レポートの一致、依存Drift検証などの厳格な完了条件。
5.  **スキルサイズ・コンテキストの管理 (v104)**:
    *   Response truncated 対策として、ジョブのロードスキルサイズ合計を100KB以下に制限。出力トークン制限（800字、3提案、詳細はファイル保存）。
6.  **checkpoint（進捗打刻・再開プロトコル）**:
    *   マイルストーンごとに進捗を打刻し、再実行時に完了ステップを自動スキップ。

### 現状の課題と対策の必要性
*   **無料/低コストモデル（nous等無料モデル）の特性への適応**:
    *   現在、Nous の `:free` モデル（`meituan/longcat-2.0:free` 等）など低コスト・無料モデルの活用が必須。これらのモデルは知識が古い（2024年以前）ため、最新のXのUIやGraphQL仕様（REST 403誤判定問題など）をプロンプトまたはツール側で静的知識として補う必要がある。
*   **Done Guard / 完了判定の無限ループ**:
    *   `worker` が `kanban_done_guard.py` を通過できずに同じテストやコマンドを何度も繰り返し（ repeated_exact_failure ）、セッションの最大イテレーションを使い果たす事故が発生している。
*   **スキルの肥大化**:
    *   手動でのスキル管理が追い付かず、知らず知らずのうちに SKILL.md が肥大化。再度 Response truncated 障害を起こす潜在的リスク。

## 3. Kenshoへの具体的適用提案（アクションプラン）

Kenshoの既存の強固なハーネスをベースに、最新プラクティスを接ぎ木（適用）するための4つの具体的施策を提案します。

---

### 提案①：進捗差分（Progress Delta）による停滞・無限ループ対策の高度化

#### 現状
`loop_health.sh` は Kanban 状態の `stagnation_streak`（同じタスクが ready / running のまま滞留している日数）を見ていますが、1つのセッション（実行イテレーション中）で Worker が同じ場所で空回りしているかどうかはリアルタイム検知できません。

#### 適用策
Worker の `nightly-worker` 実行時、および `kanban_done_guard.py` の前後において、**Progress Delta（進捗差分）**の概念を導入します。

1.  **サブゴールの構造化**:
    Worker の実行計画（実装前プラン）に、完了すべきサブゴールを明示的に持たせる（既存の `[checkpoint]` の仕組みを拡張）。
2.  **Progress Delta の打刻**:
    Worker が `[checkpoint] step N done` を打刻する際、`Progress Delta = 1`（1ステップ進んだ）とみなします。
    もし 2 ターン連続で checkpoint の打刻がない、または `Progress Delta = 0` の場合、**「ループ停滞（Reasoning Loop）」**とみなし、Worker は自律的にそのタスクを `kanban_block(reason='Progress Delta = 0 for 2 turns')` にして人間にエスカレーションします。

**期待効果**: 1セッション中の無駄なトークン消費と時間浪費（max-turnsに達するまでの空回り）を即座に自動停止。

---

### 提案②：Debounce Guard（重複コマンド/同一エラー実行の自動遮断）

#### 現状
Worker や QA が同一のツールコール（例: 同じ patch 適用、同じテスト実行 `pytest` ）をエラーが出ているにもかかわらず繰り返してしまう現象（`repeated_exact_failure`）が発生しています。

#### 適用策
Kensho AIチームの実行ハーネス（特に `nightly-worker` や各種自動スクリプト、または `kanban_done_guard.py` の呼び出し部分）に、**Debounce Hook（指紋ベースの重複ガード）**を組み込みます。

1.  **コマンド指紋（Command Fingerprint）の記録**:
    実行したシェルコマンドやツールコールとその出力を一時的なヒストリファイル（`data/action_fingerprints.json`）に記録。
2.  **2回連続同一失敗時の3回目遮断**:
    *   直近2回の実行において、「全く同じコマンド」かつ「エラーまたは同一の検証FAIL結果」であった場合、3回目の実行を自動でスキップ（ブロック）します。
    *   ブロック時には、LLM（Worker）に対して明確なエラー文を返します：
        ```
        [DEBOUNCE BLOCK] 同一コマンドの連続失敗を検出しました。
        コマンド: {command}
        エラー: {last_error}
        方針を修正するか、自動解決不能と判断した場合は kanban_block してください。同じ試行を繰り返すことは禁止されています。
        ```

**期待効果**: セッションの枯渇を未然に防ぎ、自己崩壊ループを防止。

---

### 提案③：ACE/MCE準拠「プレイブック型コンテキスト管理（自動スキル衛生化）」

#### 現状
Kenshoの `ai-team-improvement` スキルはすでに階層化（references/へ希少知識を移設）して肥大化（Response truncated FAILED）を防いでいますが、これをさらに自動化・定常化します。

#### 適用策
ACE/MCEの思想を適用し、**「自動スキル衛生化（Auto Skill Hygiene）」**を cron 駆動で実装します。

1.  **構造化されたプレイブックファイル (Playbook.json / Markdown)**:
    ルールやピットフォールを単なるマークダウンのフラットテキストから、`{ "id": "REST_403_MISCLASS", "title": "API 403誤判定対策", "content": "..." }` のようにJSONまたは明示的にインデックスされた構造で保持。
2.  **`kensho-skill-hygiene-daily` ジョブの強化**:
    *   現在実装済みの監視層（SKILL.md > 20KB、合計 > 100KBで警告）に、「自動階層化スクリプト」を追加。
    *   SKILL.md のサイズが閾値を超えた場合、3日以上参照されていない教訓や特定エラーのトラブルシューティング（希少知識）を、自動的に `references/` ディレクトリ配下のMarkdownに切り出し、SKILL.md からは `[移設済み]` のインデックス参照リンクのみを残すように `skill_manage` で自動パッチを当てる。

**期待効果**: スキルのサイズを常に 15KB〜20KB 以内に自動維持。Response truncated 障害の発生確率を永久に 0% に。

---

### 提案④：低コスト・無料モデルに特化した「静的知識(ρ)の注入」と「終端シグナルの明確化」

#### 現状
ユーザー方針により、AIチームは `nous (meituan/longcat-2.0:free)` などの無料モデルや fireworks などの低コストモデルを優先利用します。これらのモデルは知識が古いため、最新のX API仕様（RESTが403を返すエラー、GraphQL移行、HttpOnlyクッキー等）に対応できず、APIエラーを「既にフォロー済み」と誤検知して偽Doneを出しやすい課題があります。

#### 適用策
1.  **静的知識 ρ のインジェクション**:
    無料モデルが「最新のXの振る舞い」を正しく推論できるよう、システムプロンプトの冒頭に、**「最新のXのAPI制約・仕様（2026年時点）」の静的知識 ρ**（例: `HttpOnly ct0の取得方法`、`REST endpoint 403はエラーであり完了ではない`、`GraphQL FavoriteTweetへの移行`）を必ずコンテキストに差し込みます。
2.  **明確な終端（SUCCESS / FAILED）のツール設計**:
    *   KenshoのAPIアクションスクリプト（`api_actions.py` や `applier.py`）の戻り値を、曖昧なステータスコード（403を成功扱いなど）から、**「明確な SUCCESS 判定」または「明確な FAILED：理由」**に統一します。
    *   ツールが `SUCCESS` を返すまでは絶対に完了判定とさせず、`FAILED: ct0_expired` などの場合は明確に「失敗」として Failure Ceiling（連続失敗上限）に加算します。

**期待効果**: 無料モデル利用時の誤推論・誤判定（偽Done）を防ぎ、低コストかつ極めて安全（BOT検出回避）な応募運用を維持。

## 5. 結論と実装ステップ

Kenshoはすでに非常に高度な自律ループを形成していますが、今回の提案を適用することで「空回り」「肥大化」「誤検知」といった自律型マルチエージェント特有の宿命的課題を、**メタ・ハーネス（実行プレーン）側のアップデート**によって完全に制御できるようになります。

### 推奨される実装ステップ
1.  **フェーズ1（即時適用・低コスト）**:
    *   `applier.py` / `api_actions.py` の戻り値を「明確な SUCCESS / FAILED 終端シグナル」にリファクタリング。
    *   Worker プロンプトへの「Progress Delta（進捗差分チェックポイント）」ルールの厳格化。
2.  **フェーズ2（ハーネス強化）**:
    *   `kanban_done_guard.py` に「同一コマンド・失敗の連続実行（Debounce Guard）」機能を組み込み、3回目は自動でブロック。
3.  **フェーズ3（継続的最適化）**:
    *   `kensho-skill-hygiene-daily` に、SKILL.md から `references/` への「自動知識退避（自動階層化）スクリプト」を組み込み、スキル衛生を自律自動化。
